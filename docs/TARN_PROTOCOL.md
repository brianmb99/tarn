# Tarn Protocol — Working Draft

**Status:** Active design discussion (Issue #69)
**Last updated:** 2026-04-09

Tarn is an app-agnostic platform for storing encrypted, user-owned data permanently on Arweave. This document defines the complete protocol: identity, authentication, encryption, and data operations. Nothing here references Bookish or any specific app.

---

## Key Hierarchy

```
email + password (user input, never leaves client)
  -> master_key                  PBKDF2-SHA256(password, SHA-256(email + domain), 600K iterations)
    -> credential_lookup_key     SHA-256(master_key + 'tarn-credential-lookup-v1')
    -> credential_encryption_key SHA-256(master_key + 'tarn-credential-encrypt-v1')
    -> signing_key_pair          ECDSA P-256 derived from master_key
                                   -> public_key   (sent to API, stored in D1 and on Arweave)
                                   -> private_key  (never leaves client)

data_encryption_key:
  At account creation: data_encryption_key = credential_encryption_key (same key)
  After credential change: data_encryption_key = ORIGINAL credential_encryption_key (frozen)
  The data_encryption_key never changes. Credential changes re-wrap it, not re-derive it.

data_lookup_key:
  Generated by the API at registration. Random, unique, opaque.
  Not derived from any client secret. Returned to the client at registration.
```

### Wrapped Data Key

The `data_encryption_key` is stored by the API as a **wrapped key**:

```
wrapped_data_key = AES-256-GCM(data_encryption_key, credential_encryption_key)
                               ^^^^ payload            ^^^^ wrapping key
```

At account creation, payload and wrapping key are the same key — self-encryption, redundant but intentional. The client always performs the same operation on login:

```
data_encryption_key = decrypt(wrapped_data_key, credential_encryption_key)
```

No branching for "first login" vs. "post-credential-change login." Uniform client code path regardless of credential history.

After a credential change, `wrapped_data_key` becomes `encrypt(ORIGINAL_data_encryption_key, NEW_credential_encryption_key)`. The client decrypts with the new credential key and recovers the original data encryption key. All existing data remains decryptable.

### Authentication via Signing Key

Authentication uses an ECDSA P-256 signing key pair derived deterministically from `master_key`. The client signs challenges with the private key; the API verifies with the stored public key. No secrets are ever transmitted to or stored by the API.

This is the same pattern as the existing EIP-191 wallet signature model, without the Ethereum wallet or ethers.js dependency. WebCrypto supports P-256 natively (`crypto.subtle.sign('ECDSA', ...)`, `crypto.subtle.verify('ECDSA', ...)`).

## Security Model

### Threat model

Tarn assumes credentials are never compromised. Credential changes are a convenience feature (e.g., new email address), not a security remediation tool.

### No forward secrecy on credential change

Changing credentials does NOT provide forward secrecy for data encryption. Old credential mappings persist on Arweave (immutable). An attacker with old credentials can always:

1. Derive the old `credential_lookup_key`
2. Find the old credential mapping blob on Arweave
3. Unwrap the old `wrapped_data_key` with the old `credential_encryption_key`
4. Decrypt all data (past and future — `data_encryption_key` never changes)

This is inherent to immutable storage. Per-entry key rotation could mitigate this but would add significant complexity. For the target use case (consumer apps storing reading lists, notes, collections), this trade-off is acceptable. Applications storing financial or medical data should evaluate whether this threat model is sufficient.

### What the API knows vs. doesn't know

| API sees                          | API never sees                   |
|----------------------------------|----------------------------------|
| public_key (for signature verification) | private_key (signing)      |
| credential_lookup_key            | master_key                       |
| data_lookup_key (it generated it)| email, password                  |
| wrapped_data_key (opaque blob)   | data_encryption_key              |
| encrypted data blobs (opaque)    | credential_encryption_key        |
|                                  | plaintext of any data blob       |

No secrets are stored by the API. The public key is public. Zero-knowledge preserved for all key material that protects user data.

## Arweave Tag Scheme

All blobs on Arweave carry these tags:

| Tag  | Meaning                    | Example                   |
|------|---------------------------|---------------------------|
| App  | App identifier             | `bookish`, `winelist`     |
| Type | Blob type                  | `cred`, `entry`, `acct`   |
| Lk   | Lookup key (64-char hex)   | `a3f8...`                 |
| Enc  | Encryption method          | `aes-256-gcm`             |
| V    | Protocol version           | `0.3.0`                   |

For credential blobs: `Lk` = `credential_lookup_key`.
For data blobs: `Lk` = `data_lookup_key`.

Additional tags for versioning (data blobs only):

| Tag  | Meaning                          |
|------|----------------------------------|
| Prev | Txid of prior version (edits)    |
| Op   | Operation flag (`tombstone`)     |
| Ref  | Txid referenced by tombstone     |

## Blob Format

All data blobs are AES-256-GCM encrypted by the client. Wire format:

```
[IV: 12 bytes] [ciphertext + GCM tag: N bytes]
```

GCM tag is 16 bytes, appended to ciphertext by WebCrypto. Plaintext is UTF-8 encoded JSON.

IV must be randomly generated (12 bytes via `crypto.getRandomValues`) for each encryption operation. IV reuse with the same key is catastrophic for AES-GCM security.

## Credential Mapping on Arweave

The credential mapping blob is **not encrypted**. It contains:

```json
{
  "data_lookup_key": "<64-char hex>",
  "wrapped_data_key": "<base64-encoded AES-256-GCM ciphertext>",
  "public_key": "<base64-encoded ECDSA P-256 public key>"
}
```

No value here is secret:
- `data_lookup_key` is already in every data entry's `Lk` tag on Arweave — publicly visible
- `wrapped_data_key` is useless without `credential_encryption_key` (derived from email+password via PBKDF2 at 600K iterations)
- `public_key` is public by definition

Storing the credential mapping unencrypted:
- Lets the API write it directly during registration (single API call, no second client round-trip)
- Enables full API self-healing from Arweave: if D1 is destroyed, `accounts` table can be completely rebuilt (all fields are in the credential mapping blob or its tags)
- Avoids asymmetric crypto complexity (ECDH/ECIES) for negligible privacy gain

## App Identity

Apps are first-class Tarn identities. An app registers with Tarn using the same ECDSA signing key model as users. App identities allow apps to manage user write rules (e.g., subscription tiers) via authenticated API calls.

### App registration

App registration is a privileged operation (initially manual, eventually a developer portal):

```
App generates ECDSA P-256 key pair
Tarn operator registers: { app_id, public_key, role: 'app' }
Stored in D1 and on Arweave: Type: 'app-reg', Lk: app_id
```

### App authentication

Same challenge-response protocol as users:

```
POST /api/v1/auth/challenge  { credential_lookup_key: <app_id> }
POST /api/v1/auth/verify     { credential_lookup_key: <app_id>, nonce, signature }
-> JWT with { sub: <app_id>, role: 'app' }
```

### App wallets for Arweave storage

Each app has its own Arweave/Turbo wallet for paying storage costs. The wallet private key is stored as a secret in the Tarn API environment (Cloudflare Worker secret). When the API forwards data to Turbo/Arweave, it uses the wallet associated with the `App` tag.

- Wallet setup is manual (part of app registration)
- Balance must be monitored and topped up — this is an operational concern, not a protocol concern
- For Turbo: data items under 100KB are currently free, so for apps that keep entries small, the wallet may not need frequent funding

## Write Authorization Rules

Write access is controlled by a **rules** array on each user account. At write time, the API evaluates all rules — **every rule must pass** for the write to be allowed. Unknown rule types **fail closed** (deny).

Rules are set by authenticated app identities (see App Identity). The entire rules array is **replaced** on each update (no merging). The app owns the subscription/payment state and sends the complete rule set each time.

### Rule types (v1)

**`max_entries`** — user has fewer than N entries matching the filters

```json
{
  "type": "max_entries",
  "limit": 1000,
  "since": "2026-04-01T00:00:00Z",
  "app": "bookish",
  "entry_type": "entry"
}
```

All filter fields (`since`, `app`, `entry_type`) are optional. Omitted = not filtered.

Tarn evaluates: `SELECT COUNT(*) FROM entries WHERE lookup_key = ? AND app = ? AND type = ? AND cached_at > ?`

**`max_bytes`** — this individual entry is smaller than N bytes

```json
{
  "type": "max_bytes",
  "limit": 102400
}
```

Tarn evaluates: `payload.byteLength <= limit` (checked before forwarding to Arweave).

Note: Turbo currently provides free uploads under 100KB. Apps that want to avoid Arweave payment costs should set `max_bytes` to 102400 (100KB).

**`expires`** — the current time is before this timestamp

```json
{
  "type": "expires",
  "at": "2027-04-01T00:00:00Z"
}
```

Tarn evaluates: `Date.now() < at`

### Rule evaluation at write time

```
For each rule in account.rules:
  if rule.type is unknown -> DENY (fail closed)
  if rule evaluates to false -> DENY
If all rules pass -> ALLOW
If no rules exist -> ALLOW (default: unrestricted)
```

### Rules on Arweave

When an app sets rules for a user, Tarn persists to Arweave:

```
Tags: { Type: 'app-config', Lk: data_lookup_key, App: <app_id>, V }
Body: { rules: [...], set_by: <app_id>, timestamp: <ISO 8601> }
```

Not encrypted — rules are not sensitive (entry counts and expiry dates). This enables full D1 recovery: scan Arweave for `Type=app-config`, latest per `data_lookup_key + app_id` wins.

### Future rule types (not v1, but the model supports them)

- **`rate_limit`** — max N writes per time window
- **`allowed_types`** — restrict which `Type` values the user can write
- **`requires_tag`** — entry must carry a specific tag

## API State

The API (Cloudflare Worker + D1) maintains:

**D1 `accounts` table:**
```sql
credential_lookup_key TEXT PRIMARY KEY,
public_key TEXT NOT NULL,             -- ECDSA P-256 public key, base64
data_lookup_key TEXT NOT NULL UNIQUE,
wrapped_data_key TEXT NOT NULL,       -- base64-encoded encrypted data_encryption_key
rules_json TEXT,                      -- JSON array of write authorization rules (NULL = unrestricted)
created_at INTEGER NOT NULL
```

**D1 `apps` table:**
```sql
app_id TEXT PRIMARY KEY,              -- e.g., 'bookish'
public_key TEXT NOT NULL,             -- ECDSA P-256 public key, base64
created_at INTEGER NOT NULL
```

**D1 `entries` table** (cache of Arweave data):
```sql
txid TEXT PRIMARY KEY,
app TEXT,
type TEXT,
lookup_key TEXT,              -- data_lookup_key or credential_lookup_key
prev_txid TEXT,
is_tombstone INTEGER,
tombstone_ref TEXT,
block_timestamp INTEGER,
tags_json TEXT,
cached_at INTEGER
```

**Rebuild from Arweave:**
- `entries`: Fully rebuildable from Arweave GraphQL queries (scan by `App` + `Type` tags)
- `accounts`: Fully rebuildable from `Type=cred` blobs. `credential_lookup_key` from `Lk` tag; `data_lookup_key`, `wrapped_data_key`, and `public_key` from blob body. `rules_json` rebuilt from `Type=app-config` blobs. No user action required.
- `apps`: Fully rebuildable from `Type=app-reg` blobs on Arweave.

## Flows

### 1. Register (new account)

```
CLIENT (local):
  1. Derive master_key from email + password (PBKDF2)
  2. Derive credential_lookup_key, credential_encryption_key, signing_key_pair
  3. data_encryption_key = credential_encryption_key (same key at creation)
  4. wrapped_data_key = encrypt(data_encryption_key, credential_encryption_key)
     (Self-encryption — redundant, but keeps client logic uniform)

CLIENT -> API:
  5. POST /api/v1/auth/register
     Body: { credential_lookup_key, public_key, wrapped_data_key }

API:
  6. Check credential_lookup_key not already in use (-> 409 Conflict if exists)
  7. Generate data_lookup_key (random, guaranteed unique in D1)
  8. Store in D1: { credential_lookup_key, public_key, data_lookup_key, wrapped_data_key }
  9. Persist credential mapping to Arweave:
     Tags: { Type: 'cred', Lk: credential_lookup_key, V }
     Body: { data_lookup_key, wrapped_data_key, public_key }
  10. Return: { data_lookup_key }
```

Single API call. API persists to both Arweave and D1.
App-level data (display name, settings, etc.) is created via normal "create data" calls afterward — not part of identity.

### 2. Sign in (existing account, any device)

```
CLIENT (local):
  1. Derive master_key from email + password
  2. Derive credential_lookup_key, credential_encryption_key, signing_key_pair

CLIENT -> API:
  3. POST /api/v1/auth/challenge
     Body: { credential_lookup_key }
     API looks up account by credential_lookup_key.
     Returns: { nonce, data_lookup_key, wrapped_data_key }

CLIENT (local):
  4. Sign nonce with private_key -> signature
  5. data_encryption_key = decrypt(wrapped_data_key, credential_encryption_key)

CLIENT -> API:
  6. POST /api/v1/auth/verify
     Body: { credential_lookup_key, nonce, signature }
     API verifies signature against stored public_key.
     Returns: { jwt }

CLIENT:
  7. Done. Has:
     - data_lookup_key (to find data on Arweave)
     - data_encryption_key (to decrypt data)
     - JWT (to authorize writes)
```

Two API calls, no secrets transmitted. `data_lookup_key` and `wrapped_data_key` are returned in the challenge (both non-secret), so the client can begin decryption while signing.

### 3. Create data

```
CLIENT (local):
  1. Already signed in: has data_encryption_key, data_lookup_key, JWT
  2. Build payload (app-defined JSON schema)
  3. Encrypt with data_encryption_key -> encrypted_blob

CLIENT -> API:
  4. POST /api/v1/entries  [JWT]
     Tags: { App, Type, Lk: data_lookup_key, Enc, V }
     Body: encrypted_blob

API:
  5. Verify JWT
  6. Check Lk tag matches JWT subject (data_lookup_key)
  7. Evaluate write authorization rules (see Write Authorization Rules)
     -> 403 if any rule fails
  8. Forward to Arweave (via Turbo bundler, using app's wallet)
  9. Write-through to D1 cache
  10. Track pending tx
  11. Return: { txid, status: 'pending' }
```

### 4. Retrieve data

```
CLIENT -> API:
  1. GET /api/v1/entries?app={app}&type={type}&key={data_lookup_key}
     No auth required. IP rate-limited.
     Returns: resolved list of { txid, tags }
     (Resolution: tombstones applied, Prev-chains resolved, latest versions only)

  2. For each txid: download encrypted blob from Arweave gateway

CLIENT (local):
  3. Decrypt each blob with data_encryption_key -> plaintext
```

Reads are unauthenticated. Data is on Arweave (public, encrypted). Auth on reads would only protect the cache layer, not the data. Security comes from encryption, not access control. This also enables a permanent, static data export page that works without any API.

### 5. Update data

```
CLIENT (local):
  1. Modify entry, encrypt with data_encryption_key -> encrypted_blob

CLIENT -> API:
  2. PUT /api/v1/entries/{prior_txid}  [JWT]
     Tags: { App, Type, Lk: data_lookup_key, Prev: prior_txid, Enc, V }
     Body: encrypted_blob

API:
  3. Verify JWT
  4. Verify prior_txid exists and belongs to this data_lookup_key
  5. Forward to Arweave, cache in D1
  6. Old entry superseded via Prev-chain resolution
  7. Return: { txid, prevTxid, status: 'pending' }
```

### 6. Delete data

```
CLIENT (local):
  1. Encrypt tombstone marker with data_encryption_key -> encrypted_blob

CLIENT -> API:
  2. DELETE /api/v1/entries/{target_txid}  [JWT]
     Tags: { App, Type, Lk: data_lookup_key, Op: tombstone, Ref: target_txid, Enc, V }
     Body: encrypted_blob

API:
  3. Verify JWT
  4. Verify target_txid exists and belongs to this data_lookup_key
  5. Forward to Arweave, cache in D1
  6. Entry hidden by tombstone resolution
  7. Return: { txid, tombstoneRef, status: 'pending' }
```

### 7. Change credentials (email and/or password)

Requires knowledge of BOTH old and new credentials. Requires active session (JWT from old credentials).

```
CLIENT (local):
  1. Already signed in with old credentials: has data_encryption_key, JWT
  2. Derive NEW master_key from new email + password
  3. Derive new_credential_lookup_key, new_credential_encryption_key, new_signing_key_pair
  4. new_wrapped_data_key = encrypt(data_encryption_key, new_credential_encryption_key)
     (Re-wraps the SAME data_encryption_key with the new credential key)

CLIENT -> API:
  5. PUT /api/v1/auth  [JWT from old credentials]
     Body: { new_credential_lookup_key, new_public_key, new_wrapped_data_key }

API:
  6. Verify JWT (proves identity via old credentials)
  7. Check new_credential_lookup_key not already in use (-> 409 Conflict)
  8. Update D1: replace credential_lookup_key, public_key, wrapped_data_key
     (data_lookup_key unchanged)
  9. Persist new credential mapping to Arweave:
     Tags: { Type: 'cred', Lk: new_credential_lookup_key, V }
     Body: { data_lookup_key, new_wrapped_data_key, new_public_key }
  10. Return: OK
```

data_lookup_key never changes. All existing data blobs on Arweave are untouched. Only the credential wrapping and signing key change.

Post-change login is identical to Flow 2 — uniform client code path:
- Derive new keys -> challenge/verify -> get { data_lookup_key, new_wrapped_data_key }
- `decrypt(new_wrapped_data_key, new_credential_encryption_key)` -> original `data_encryption_key`

### 8. D1 Recovery (after data loss)

If D1 is destroyed, both tables can be rebuilt.

```
Entries table:
  Self-heals on cache miss — API queries Arweave, populates D1.

Accounts table:
  1. API scans Arweave for Type=cred blobs
  2. For each: extract from Lk tag and blob body:
     credential_lookup_key, data_lookup_key, wrapped_data_key, public_key
  3. Insert complete rows into D1 accounts
  4. If multiple cred blobs share a data_lookup_key (credential changes),
     keep the latest (highest block_timestamp)
  5. Normal login resumes — no user action required
```

Full self-healing. All fields are present in the Arweave credential mapping (public_key is in the blob body, not a secret). No re-registration flow needed.

### 9. Set user write rules (app -> API)

```
APP -> API:
  1. App authenticates via challenge/verify (same as user login)
     -> JWT with { sub: <app_id>, role: 'app' }

  2. PUT /api/v1/accounts/{data_lookup_key}/rules  [JWT with role: 'app']
     Body: { rules: [...] }

API:
  3. Verify JWT has role: 'app'
  4. Verify user has entries tagged with this app_id (they're the app's user)
  5. Replace rules_json in D1 accounts table
  6. Persist to Arweave:
     Tags: { Type: 'app-config', Lk: data_lookup_key, App: <app_id>, V }
     Body: { rules: [...], set_by: <app_id>, timestamp }
  7. Return: OK
```

Rules replace in full. The app sends the complete rule set every time.

## Client <-> API Summary

### Auth endpoints

```
POST /api/v1/auth/register
  Body: { credential_lookup_key, public_key, wrapped_data_key }
  Auth: none
  Returns: { data_lookup_key }
  Errors: 409 (credential_lookup_key in use)

POST /api/v1/auth/challenge
  Body: { credential_lookup_key }
  Auth: none
  Returns: { nonce, data_lookup_key, wrapped_data_key }
  Errors: 404 (unknown credential_lookup_key)

POST /api/v1/auth/verify
  Body: { credential_lookup_key, nonce, signature }
  Auth: none (signature IS the auth)
  Returns: { jwt }
  Errors: 401 (invalid/expired nonce, bad signature)

PUT /api/v1/auth
  Body: { new_credential_lookup_key, new_public_key, new_wrapped_data_key }
  Auth: JWT
  Returns: 200 OK
  Errors: 401, 409 (new credential_lookup_key in use)
```

### App endpoints

```
PUT /api/v1/accounts/{data_lookup_key}/rules
  Body: { rules: [...] }
  Auth: JWT with role: 'app'
  Returns: 200 OK
  Errors: 401, 403 (not an app JWT, or user has no entries for this app)
```

### Data endpoints

```
POST /api/v1/entries
  Headers: Authorization: Bearer <jwt>, X-Arweave-Tags: [...]
  Body: <encrypted blob bytes>
  Auth: JWT
  Returns: { txid, status: 'pending' }
  Errors: 401, 403 (Lk mismatch), 413 (too large)

GET /api/v1/entries?app={app}&type={type}&key={data_lookup_key}
  Auth: none (IP rate-limited)
  Returns: { entries: [{ txid, tags }], total }

PUT /api/v1/entries/{prior_txid}
  Headers: Authorization: Bearer <jwt>, X-Arweave-Tags: [...]
  Body: <encrypted blob bytes>
  Auth: JWT
  Returns: { txid, prevTxid, status: 'pending' }
  Errors: 401, 404 (prior_txid not found or not owned)

DELETE /api/v1/entries/{target_txid}
  Headers: Authorization: Bearer <jwt>, X-Arweave-Tags: [...]
  Body: <encrypted blob bytes>
  Auth: JWT
  Returns: { txid, tombstoneRef, status: 'pending' }
  Errors: 401, 404 (target_txid not found or not owned)
```

## Design Decisions

### Why self-encryption at registration
At registration, `data_encryption_key == credential_encryption_key`, so `wrapped_data_key = encrypt(key, key)` is redundant. But it means login is always the same code path: `decrypt(wrapped, cred_key) -> data_key`. No special-casing for "never changed credentials" vs. "changed credentials N times." Client simplicity is worth the one redundant operation.

### Why challenge-response signing instead of transmitting auth credentials
The client proves identity by signing a nonce with a private key derived from `master_key`. The API verifies with the stored public key. No secrets are transmitted (even over HTTPS) and no secrets are stored by the API. This is the same proven pattern as EIP-191 wallet signatures, without the Ethereum dependency.

### Why reads are unauthenticated
Data lives on Arweave permanently and publicly (encrypted). The `data_lookup_key` is in Arweave tags on every entry. Anyone scanning Arweave can find and download encrypted blobs for any `data_lookup_key`. Requiring auth for API reads would only protect the cache layer — not the data itself. A permanent, auditable, API-independent data export page must be possible.

### Why credential mapping is plaintext on Arweave
The credential mapping body is `{ data_lookup_key, wrapped_data_key, public_key }`. All values are either already publicly visible on Arweave (data_lookup_key in entry tags) or public by definition (public_key) or encrypted (wrapped_data_key). Asymmetric encryption would hide the link between credential_lookup_key and data_lookup_key, but this link is already inferable from data entry grouping. Clean upgrade path exists if needed later.

### Why API generates data_lookup_key
The API generates `data_lookup_key` (random) rather than deriving it from client secrets. This means:
- Credential changes don't affect data indexing (no tag migration on Arweave)
- API guarantees uniqueness (checks D1 before assigning)
- The value is not secret (visible in Arweave tags) so API generating it doesn't compromise zero-knowledge

### Tarn is app-agnostic
The `App` tag is set by the client app. Tarn treats it as an opaque string for filtering. Multiple apps can share the same Tarn identity (same `data_lookup_key`), each writing blobs with their own `App` value. App isolation is by tag filtering convention, not protocol enforcement.

## Open Questions

1. **Signing key derivation details:** How exactly to derive a deterministic ECDSA P-256 key pair from `master_key` using WebCrypto. P-256 private keys must be integers in [1, n-1]. Derivation: `SHA-256(master_key + 'tarn-signing-v1')` reduced mod n. Need to verify WebCrypto allows importing raw private key material for P-256.

2. **Protocol versioning:** The `V` tag indicates protocol version. When derivation parameters change (e.g., PBKDF2 -> Argon2id, iteration count increase), clients need to know which method was used. Options: version field in credential mapping body, or a dedicated `Kdf` tag on credential blobs.

3. **Rate limiting on registration:** Registration is unauthenticated. Each registration writes to Arweave (storage cost). IP rate limiting is sufficient for now. CAPTCHA or proof-of-work may be needed at scale.

4. **Multiple credential mappings after changes:** After credential changes, multiple `Type=cred` blobs exist on Arweave with different `Lk` values, all pointing to the same `data_lookup_key`. On cache rebuild, latest (highest `block_timestamp`) wins. Old credential mappings remain on Arweave permanently — this is a minor information leak (reveals credential change history via shared `data_lookup_key`). Acceptable for v1.

5. **App wallet monitoring:** Each app's Arweave/Turbo wallet needs balance monitoring and top-up. This is an operational concern — alerting, thresholds, who tops up. Not a protocol question, but needs operational tooling.
